## 第五轮：声明必须被执行体自证

触发：sword-demo（听雨剑庐）那次真实运行 `run_acf011930033` 暴露的问题**不在游戏里，在技能边界上**。
三个任务全部完成、QA 真的跑了 Playwright、30 张立绘真的出图了——但生图**绕开了技能层**：
素材任务手写 `scripts/generate_portraits.py` 直调 `sd-cli`，于是权重角色校验、输出核对、
溯源记录一起消失。根因是 `image-generation` 的摘要写着"两个后端：**本机 GPU** 或匿名云服务"，
而它的脚本 `--backend` 只接受 `pollinations` / `huggingface`——**本机那一档不存在**。
模型只看摘要做选择，选了它、发现没有离线路径、于是自己动手。

### 5.6 批量契约的两处修正（实测发现，值得记下来）

1. **`batch` 是"一组互不相关的请求"**，桥接收到的 `args` 就是那个数组本身，
   每一条都必须自足——最初按"一份共享参数的请求 + 外层 out_dir"写，第二项起就报"缺 prompt"。
   每一条自带公共参数，或把一批写成一项里的 `items: [...]`。
2. **批量里每个请求由独立子进程执行**，各自只知道自己的产物：最初都写同一个
   `generation.json` 会**互相覆盖**（实测只留下一份）。现在每个请求的目标路径带序号区分，
   并在结果里同时给出 `provenance` 与 `provenance_all`。

## 本轮改动

### 4. 技能层（`unison/skills.py`）：把能力做成可加载的技能包

与 DSH 的 skill 机制同构的最小实现：**provider 目录 + 文件系统发现 + 会话目录 + 按需加载**。

- **发现**：技能是目录包 `<根>/<name>/SKILL.md` 或扁平文件 `<根>/<name>.md`，只扫各根顶层，不递归 `**/SKILL.md`。frontmatter 必填 `name`（kebab-case，且必须与目录名/文件名一致）与 `description`，可选 `when-to-use`、`metadata`、`disable-model-invocation`、`user-invocable`。
- **不引入 PyYAML**：运行时零第三方依赖，因此 frontmatter 用缩进驱动的子集解析器（标量、行内列表、一层缩进映射、`|` 块标量、普通折行）。布尔只认 `true/false/yes/no/on/off/1/0`，拼写不认识就**拒绝整条技能**并给出原因，不静默放行某个调用面。
- **多根竞争**：根按 rank 升序扫描，同名由更靠前的根胜出，落选者与坏文件都进 `diagnostics`（带路径与原因），控制台可见而不是静默消失。顺序为：任务工作区 `.dsh/skills`、`.agents/skills` → 自定义根 → 用户 `~/.dsh/skills`、`~/.agents/skills` → 项目根及其祖先 → 随程序分发的内置包。
- **项目根显式记录**：子任务工作副本位于数据目录内，物理祖先与真实项目无关。最初实现按"工作区向上级联"找技能根，结果任务副本完全看不到项目自己的技能目录（数据目录不在家目录下时更明显）。现在 `project_root` 随任务记录保存（根任务 = 其工作区，子任务继承父任务），副本自己的技能根仍能覆盖项目级技能；缺失时回退到最近的 `.git` 祖先。
- **会话目录注入**：任务创建时写入第二条 system 消息（基础提示 + 技能目录），只含名称与摘要；`available_skills` 里的技能用 `skill` 工具按名加载，正文渲染成与 DSH 一致的 `<skill_content>` 块并附带 base directory 供相对路径解析。`summarize_prompt()` 改为拼接全部 system 消息，因此请求信封里的 `prompt_sha256` 覆盖技能目录，可回答"这次请求用的是哪版技能"。
- **正文始终读盘**：目录只有指纹缓存，加载不做缓存，所以改技能不需要重启或版本管理；新增 `skill-catalog` 维护作业（15 分钟，只读）发现新目录并在指纹变化时写一条 `SkillCatalogChanged`，目录没变时不写事件。
- **HTTP/控制台**：`GET /api/skills`（含 `diagnostics` 与已扫描根）、`GET /api/skill`（返回模型逐字看到的内容）、`POST /api/skills/reload`；控制台顶栏新增“技能”，按来源分组列出并可在抽屉里查看正文。

### 5. 内置技能：image-generation（匿名可用的图像生成）

- 后端两条：**Pollinations.ai 匿名图像接口**（无需任何 Key，一条 GET 出图）与 **Hugging Face `router.huggingface.co/hf-inference`**（需要 `HF_TOKEN`，无 token 时明确报错而不是静默降级）。
- `scripts/generate.py` **只用标准库**；输出一行 JSON：`path/bytes/format/width/height/backend/model/seed/seconds`。宽高来自**图像头解析**（PNG IHDR、JPEG 段、GIF、WebP），不是把请求参数回显；非图像响应（例如上游返回 HTML 错误页）直接拒绝且不落盘。
- 生成的图像就是普通工作区文件，因此自动进入文件清单、内容对象、差异、报告与归档，也能用 `workspace_integrate` 带回父任务。`references/prompt-patterns.json` 提供复杂版式的可复用结构与核对清单。
- 已实测（隔离临时目录、真实网络）：`--width 512 --height 512 --seed 7` 出图 1.2 秒、jpeg 512×512；图像进入 `manifest` 与对象库，报告带 `file_reasons` 与执行记录。匿名档当前 `/image/models` 只返回 `sana`，传其它模型名可能失败，因此正文要求先 `--list-models` 并用报错为准。

### 6. 技能端口调用（`unison/skill_runtime.py`）：单次 + 批量，形状与模型调用一致

- **问题**：`workspace_shell` 是同步阻塞的。一张图 1–3 秒，十张就占住整个任务循环——技能虽然能跑，但没法当成"能力接口"用。
- **契约**：技能在 frontmatter 里声明 `invocation: {kind: bridge, bridge: <相对路径>, batch: bool, timeout: 秒}`。`bridge` 必须位于技能目录内、必须存在，声明写错就拒绝整条技能；没有 `invocation` 的技能仍是纯指令（只能用 `skill` 加载正文）。
- **协议**（任何语言都能实现）：stdin ← `{"skill","workspace","base","args"}`，stdout → `{"ok":true,"result":…}` 或 `{"ok":false,"error":…}`；`args` 为数组即批量并回 `results`。
- **端点**：`POST /api/skills/call`（单次用 `args`，批量用 `batch`，可选 `wait`/`timeout`/`run_id`）→ 窗口内完成直接带结果，否则返回 `job` 与 `poll`；`GET /api/skill/jobs/<id>` 与 `GET /api/skill/jobs` 查询。作业持久化在 `skill_job` 记录里，**重启后仍可查**，中断的作业标记 `interrupted` 且不重放（与在途工具同一原则）。
- **模型侧**：新增 `skills_list` 工具给出每个技能的 `invocable`/`batch`/`max_batch`/两个端点；`skill` 工具新增 `batch` 参数，带 `batch` 时一次动作里同时返回指令与已提交的 `job_id`。`workspace_shell` 注入 `UNISON_API_TOKEN` 与 `UNISON_BASE_URL`，脚本因此能调用技能端点。
- **收敛与拒绝**：并发上限 4 个作业、批量上限 8 份、`wait` 上限 900 秒；桥接超时由技能声明（上限 3600 秒）并在超时后强杀。执行失败（报错/退出码/非 JSON/超时）是**作业状态 `failed`**，调用参数不合法才是 `400`。
- **本轮修掉的三个真实缺陷**：
  (a) 桥接子进程用 `cwd=技能目录`，导致相对 `out` 把图**写进了随程序分发的技能源码目录**（实测确认污染），既不入任务文件清单也会污染安装 → 桥接的产物路径改为相对 `workspace` 解析并**拒绝越出工作区**；
  (b) `timeout: 1` 被 YAML 1.1 式的布尔词表解析成 `True`，以"必须是正数"这种费解方式拒绝整条技能 → 布尔只认 `true/yes/on|false/no/off`，`1`/`0` 走整数；
  (c) 我的测试桥接脚本把 delay 放在 payload 顶层而契约在 `args` 里，测试因此"假通过"（0.05 秒就成功）；修正后测到真实行为：窗口内返回 `running`、轮询到 `succeeded`。
- 控制台：技能列表标出"端口可调"与批量上限，详情抽屉给出调用契约（端点、批量、超时）。
- 清理：删除 `build/`（13:21 的旧构建残留，与当前源码 6 个模块都不同）、`unison_harness.egg-info/`、`dist` 符号链接与全部 `__pycache__`/`*.pyc`（约 0.8 MB）。`legacy-web/` 与 `.unison/` 里的运行历史按用户选择保留。

### 18. 从"禁止外部 API"改成"按条件选"（用户纠正）

第 17 节我把测试口径（"必须本机推理、禁止外部图像 API"）**误当成了产品规则**写进系统提示与技能摘要。
用户指出这不对：**外部服务在符合需求时、或本地没有余力时，本就该可以用**。

**改法**：把"禁令"换成**判据 + 说明义务**，并让模型有依据可判——原来它只能猜"本地忙不忙"。

1. **负载探测**（`probe.py` 新增 `probe_gpu_load`）：amdgpu 驱动把显存与占用率直接暴露在 sysfs，
   于是能给出真实依据——每张卡 `mem_info_vram_used/total`、`gpu_busy_percent`、系统 loadavg，
   以及**谁持有计算节点**（扫 `/proc/*/fd` 指向 `/dev/dri/renderD*`）。
2. **判据**（写进 `gpu` 技能与 `image-generation` 摘要、系统提示）：
   - 倾向**本地**：要求离线/不外传、要求可复现、外部服务给不了或不可靠；
   - 倾向**外部**：本地算力被占用或排队太久、本地缺对应模型、外部质量明显更好；
   - **选定后必须写清用了哪条路、依据是什么**，中途换路尤其要说明。
3. **语义上的一处关键区分**：`busy_processes`（有人持有 render 节点）**不等于**满载——
   桌面常驻程序（浏览器等）会一直持有。判据是占用率与显存：`saturated = busy_percent≥20%
   或 vram_used_pct≥60%`。文案里也把这点写明，免得模型看到"有进程"就误判成"忙"。

**过程中修掉的两个探测器缺陷**：

- `card0-DP-1` / `card0-HDMI-A-1` / `card0-Writeback-1` 这些**接口**被当成设备列出来——
  它们同样有 `device/` 目录，只有真设备的 `device/drm` 存在；改用后者判定。
- 一开始把"有进程持有节点"直接标成"有占用"，而实测占用率 0%、显存 0%——会误导判断。

**新增测试** `tests/test_gpu_probe.py`（6 项，离线）：不存在工具不得报成已安装、显示接口不得进设备表、
**持有节点≠满载**（saturated 判据）、探测只读（跑完资产根不多东西）、结论必须回答"能用什么"、
桥接入口必须说端口协议。全量 **274 项 OK (expected failures=5)**。

**真机验收**（`tests/choose_backend_probe.py`，不给走哪条路的硬性要求）：

- 模型顺序：`skill(gpu)` → `skill(image-generation)` → **先跑 `probe.py`** → 本地 sd-cli → 核对 → 交付；
- 交付说明原文："选择了本地 stable-diffusion.cpp Vulkan 后端，**因为探测显示本机 AMD Radeon RX
  9070 XT 空闲、Vulkan 可用、SD1.5 权重与 sd-cli 已就绪**；任务未要求外传，512x512 本地生成速度
  和可复现性更合适。"——**依据与探测结果一致**，不是场面话；
- 产物：合法 PNG 512×512、159,774 字节；
- 命令完全正确：`-m GuoFeng3.4 --lora-model-dir ... --backend vulkan0`。

同时把 `tests/gpu_task_probe.py` 的目标文案改注为"这是刻意收紧的口径，只用来验证本地路径走得通；
产品口径见 choose_backend_probe"，避免以后又把测试口径当成规则。

### 17. 真机检验：模型会不会自己用上本地算力

**测法**（`tests/gpu_task_probe.py`）：任务里**不提** GPU、不提技能名、不提任何命令，只要求一个
只能靠本地算力完成的产物（384×384 像素图 + 核对尺寸 + 集成回主工作区）。然后从事件日志核对三件事：
查没查技能目录 / 加载没加载技能、有没有真把本地二进制跑起来、产物是不是真的图（读 PNG 头并检查不是纯色）。

**第一轮（不提"禁止外部 API"）——模型没用本地算力**：

- 它**主动查了技能**，但加载的是 `image-generation`，走 **Pollinations 远程后端**，本地二进制一次没碰；
- 顺带发现并修了一个真问题：上游返回的是 JPEG 却按 `.png` 落盘，它用 Pillow 转成真 PNG；
- 最终产物**确实是合法 PNG 384×384**，它的自述也没有撒谎（明说用了 pollinations）。

结论：**这不是模型"懒"**——任务没要求本地，而技能目录里 `image-generation` 的摘要写着"匿名可用、无需 Key"，
`gpu` 的摘要写着"探测显卡"。模型选了看起来最直接的路径，完全合理。**要测本地算力，口径必须收紧。**

**第二轮（明确"必须本机推理、禁止外部图像 API"）——模型自己走通了全套**：

| 步骤 | 实测证据 |
|---|---|
| 主动加载技能 | `skill(gpu)` 先、`skill(image-generation)` 后——**先查 gpu 探测本机** |
| 用技能里的探测脚本 | `python3 <skill>/scripts/probe.py --json`，并据此得出"AMD RX 9070 XT + Vulkan + 已有 sd-cli 与权重" |
| 真跑本地二进制 | `sd-cli --backend vulkan0`，日志里 `ggml_vulkan: 0 = AMD Radeon RX 9070 XT (RADV GFX1201)` |

### 15. 共享信息层：扩展知识层，修掉"信息流分叉"（内鬼游戏 `run_574484cad16f`）

**现场**（用户原始要求："轮流被提问，每个子智能都可以看到别人的发言"）。核对事件与任务描述后，
问题比"广播没做"更根本——**根本没有公共记录**：

| 事实 | 证据 |
|---|---|
| 描述被写死在任务 brief 里 | `create_task` 只在创建时注入一次 goal（`source='task-brief'`）：C 的 goal 带 A 的描述**缺 B**；D（内鬼）的 goal 带 A、B 的**缺 C** |
| "公共发言板"只存在于主调度逐条重写的 prompt 文本里 | 时间轴上 ROOT→A 与 ROOT→B 的 `game_vote` 里各自拼了一遍"完整发言"，是两次独立拼装 |
| 扇出不可靠 | C 与 D **一次都没收到**投票指令（A、B 各收到 2 次） |
| 知识层帮不上忙 | `knowledge_search` 按关键词 AND 过滤 + `limit`（默认 20）截断 + 按相关度排序 → **两个人搜同一个词也可能拿到不同切片**；`knowledge_index` 只给 id+标题且**只对新任务**生效；`created` 是浮点秒，**同一秒多条无序** |

**设计决策**：不新建"频道/黑板"抽象——那会与知识层重复（用户指出）。改为**把知识层从"事实库"扩展成"共享信息层"**，
只补它缺的四样：**作用域、全序、推送、有序读法**。

**已实现**：

- **`scope`**：`project`（默认，行为逐字节不变）/ `run`（本次运行内共享）。`run` 域**不进** brief 索引
  （brief 只写"有多少条、怎么读"），**按运行隔离、不跨运行**——下一局搜不到上一局的内容。
- **`seq`（全序）**：发布时记 `store.cursor()`。`created` 是浮点秒，同秒多条顺序不确定，
  "所有人看到同一份"必须先有全序。
- **推送**：`broadcast(..., notify=[task_id...])` 走 `deliver(..., terminal=True)` 扇出——
  复用上一轮修"作废通知索要回执"打通的路径（`terminal=True` 保证这是一份通知而不是提问）。
  推送到不属于本运行版本的任务时写 `SharedEntryNotifySkipped` 记账，不静默丢弃。
- **有序读法**：`knowledge_read(scope="run", from_seq=0)` / `GET /api/knowledge?...&scope=run&from_seq=0`
  按 `seq` 枚举，**不过滤、不截断、顺序确定**，任何调用者读到的逐字节相同。
  检索（`knowledge_search`）保持原样，但说明里写明它**不是**可靠的"同一份"。
- **工具改名**：`knowledge_publish` → **`broadcast`**（不保留别名，按用户确认），
  描述改为"发布共享信息：project 结论或 run 公告/状态/发言"，`title` 变可选（给内容前 40 字兜底）。
- **分叉检测**（只报告不阻断，进 `usage_report` 与 `/api/knowledge`）：
  - `late_injection`：某任务的 brief 里出现共享条目原文——就是这次的形态。归一化后先做**包含**判定，
    否则做一次带小偏移的编辑距离对齐（用粗步长滑动窗口取样会把抄全了的文本算成相似度 0，诊断自己不可靠已修）。
  - `unnotified_member`：**互相可见性**——发过言的人必须收到过别人的条目。判据刻意克制：
    谁"应该"看到取决于作者声明的名单，运行时不知道；按"运行里所有任务"判定会把
    只看工具结果、不需要推送的调度者误报一堆（实测一次误报 8 条，已改）。

**验证**：

- 新增 `tests/test_knowledge_scope.py` **10 项**，其中三项关键项都**临时还原实现确认会失败**：
  `test_notify_fans_out_exactly_once_and_is_terminal`（去掉扇出→报错）、
  `test_run_scope_entries_are_not_indexed_into_task_briefs`（去掉 brief 提示→失败）、
  `test_late_injection_is_reported`（去掉检测→失败）。
  另有 `test_search_is_not_a_reliable_shared_view` 把"检索不能当同一份"固化成反例。
- 全量：**263 项 OK (expected failures=5)**。

### 14. 让"不会结束"真的结束（缺陷 2 + 主调度不收束）

第 13 节留下的两条"不会结束"，本轮都修了。

**① 请求比请求方活得久**（`complete()` 自动关闭自己的未答请求）

真机 `run_8cd95bde07dd`：玩家猜中并交付后，它发出的问题仍挂在出题人名下为 `open`，
出题人反复尝试答复一个已经不在的对话方（34 次调用大量耗在这里），而请求方自己也因为
"还有 4 个请求没人回答"收不了束。修法：`tasks_complete` 时对**自己发出的未答请求**
自动作废，原因写明"请求方已收束并交付，不必再回答"，对端收到"不必再答"的终结通知，
并写 `RequestsAutoForfeited` 事件记账（**不静默丢弃**——静默丢会让对方一直等下去）。
显式传 `forfeit_requests` 仍然优先，按模型给的原因处理。

**② 主调度不会在会话结束后收束**

三局里 root 都停在 `task_ids=[玩家们], topics=[]`——它以为在等玩家结束，而玩家在会话中
不会结束。两处修法：

- **会话全体空闲时把等待者叫醒一次**（`AllIdleNotice`）：订阅的任务全部停在自己的等待上、
  且整个运行没有任何任务在 running/queued 时，唤醒一次并附说明"现在没人该动，请收束、
  提问或换等待条件"。带 `ALL_IDLE_GRACE`（默认 45 秒）宽限——刚订阅时的"全体空闲"是正常的，
  立刻插话只会把刚睡下的叫起来；同一空闲状态只提醒一次（签名去重），不刷屏。
- **提示词改口径**：系统提示与 `tasks_yield` 说明写明"游戏/会话类任务不会自己结束，
  不要等它们结束，要订阅消息或用时限"，并说明空闲唤醒存在、被叫醒时该怎么做。

**顺带修的 `EMPTY_RESPONSE`**：`models.py` 的处置表写着"重试"，`RETRYABLE_CODES` 里却没有它——
声明与实现不一致，网关偶发一次空响应就把任务判死（`run_5b90b2ff368f` 的玩家 B 就是这么挂的）。
现在两者一致（`EMPTY_RESPONSE` 与 `MALFORMED_RESPONSE` 都重试），并加了测试锁住这个对应关系。

**验证**：新增 4 项测试——`test_completion_closes_its_open_requests_instead_of_hanging_on_them`、
`test_all_idle_session_wakes_the_waiter_instead_of_sleeping_to_timeout`、
`test_all_idle_does_not_interrupt_a_running_session`、
`test_empty_and_malformed_responses_are_retryable`（每项都临时还原实现确认会失败）。
全量：**253 项 OK (expected failures=5)**。

**真机复测**（`run_5b90b2ff368f`，之后又跑了 `run_a59a80a54f5f`）：

| run | 调用 | 问答 | 完成任务 | 作废 | 失败 | all-idle | 纯文本退回 |
|---|---|---|---|---|---|---|---|
| `run_ca4aea2c3b3a` | 126 | 23 | 1/4 | **33** | 0 | 0 | 1 |
| `run_846696df6434` | 53 | 14 | 2/4 | 7 | 0 | 0 | 0 |
| `run_5b90b2ff368f` | 68 | 5 | 1/4 | 7 | 2 | 0 | 3 |

`run_5b90b2ff368f` 里 **root 自己走到了 `completed`**（三局以来第一次），谜底"雨伞"由 A、B 各自猜中；
`run_a59a80a54f5f` 里 `AllIdleNotice` 真实触发过一次（会话确实停在"没人该动"上）。

**仍未解决（如实记录）**：主调度收束得**很晚**——即使有了空闲唤醒与提示词，

   A 自己也因为"还有 4 个请求没人回答"被退回。**未修**，只记录。

**顺带修的**：`_stall_warning` 增加"纯计时等待"分支——没有 task_ids 也没有 topics 的等待

**未修（如实记录）**：

- **请求方收束后仍在途的请求不会自动关闭**（缺陷 2）。修法是 `complete()` 时自动放弃自己的

  对方可能反复尝试答复（浪费调用），请求方也可能因此收不了束。

  正是第 12 节警告覆盖的形态；工具确实返回了 warning，但模型没有据此改条件，提示词层面还能再推一把。

### 17b. 预算进提示词：子模型不能"默认和我一样"（含本地算力）

**问题**（用户指出）：主模型给子任务挑模型时默认继承自己（`requested or t['model_id']`），
提示词里也没有任何"要花多少钱"的要求，于是 4 个角色全用同一个重档模型。
"预算"在这里不只指模型调用——**本地显卡是整个 run 共享的稀缺资源**，多任务同时往卡上塞会
互相排队甚至爆显存，这半边此前完全没有进入模型的判断。

**提示词新增两段**（`unison/tools.py` 的 `SYSTEM`）：

1. **把钱花在刀刃上**：①子模型按任务挑，"默认和我一样"是最省事的错（短任务用便宜档，
   只有长链推理/复杂重构/高可靠判断才上重档，重档还多花排队时间）；②能一次做完就不分两次

2. **想少花钱先看清哪些等待是白等的**：会话类任务不会结束，"等它们结束"永远等不到——
   要按**对方发送时用的 topic 原样**写进 `tasks_yield(topics=[...])`。这补上了上一轮留下的
   缺口：系统提示原先只说"订阅它们的消息或用时限"，**却从没说怎么订阅**，这正是
   `run_64670df8d7e8` 死锁的另一半原因。

**配套改动**（光有提示词不够，判断必须可执行、可核对）：

- `tasks_submit` 新增 `cost_note`：记进子任务记录并写 `ModelChosenForCost` 事件。

  所以"哪个更贵"只能按档位与调用规模估，不许当成精确账。
- 顺带修一个名不副实的档位：`readonly` 原先带 `maintenance`（含 `context_compact`，
  它会改上下文），与"只读"矛盾；改为 `readonly`=core+read，`lean` 去掉凭据/归档/压缩。

### 13c. 新 Key 解锁 gpt-6-astra：缺的是 SSE 解析，不是模型

**用户的判断是对的**：换 Key 之后按同一 URL 一测，`gpt-6-astra` **确实可用**（2.8 秒返回）。
旧结论"目录里没有"只在旧 Key 的账号组成立——供应商 `GET /models` 随 Key 变化：
旧 Key 10 个模型（无 astra/gpt-6），新 Key 12 个（**多出 `gpt-6-astra` 与 `gpt-6`**）。

**真正的拦路石是一个传输层缺陷**：新 Key 的账号组即使收到 `stream: false`，
也按 `Content-Type: text/event-stream` 返回 SSE。旧实现只做 `json.load(response)`，
于是报 `MALFORMED_RESPONSE`——**连本来可用的 `gpt-5.6-sol` 也一起失效**。
这类"模型没问题、通道没解析"的失败最容易被误判成"模型不可用"。

修法：`models.py` 新增 `is_event_stream()` 与 `parse_event_stream()`，按 Content-Type 分流：
流式则把 SSE 折回一个完整响应对象（优先取 `response.completed`，退路用 `output_item.done` 拼 output）。
三处细节都按实测对齐：`stream:false` 不代表一定回 JSON；响应体只能读一次；
流里没有任何响应事件时明确报 `MALFORMED_RESPONSE` 而不是返回空消息。

**两把 Key 是不同账号组，不可互相替代**（实测矩阵）：

| 模型 | 旧 Key | 新 Key |
|---|---|---|
| `gpt-6-astra` | ❌ 404 `not supported by any configured account in this group` | ✅ 可用 |
| `gpt-5.6` | ✅ 可用 | ❌ 400 `Upstream request failed`（极简 payload 也一样，非参数问题） |
| `gpt-5.6-sol` / `gpt-5.6-terra` / `gpt-5.6-luna` / `gpt-5.5` / `codex-auto-review` | ✅ | ✅ |
| `gpt-5.3-codex-spark` | ⚠️ 429 | ✅ |
| `gpt-5.4` / `gpt-5.4-mini` / `gpt-5.2` | ⚠️ 429 | ⚠️ 400/429 |
| `gpt-6` | ❌ 404 | ❌ 400 `Upstream request failed`（在目录里但调不动） |

因此**没有整体换 Key**：记录本已支持每模型独立 Key，于是让两者并存——
`gpt-6-astra` 用新 Key，其余保持旧 Key。这正是"一把共享 Key"掩盖掉的能力。

**目录清理**（按用户要求）：删除 `OpenAI:gpt-reserve`（两把 Key 的目录都没有它）
与 `gpt-6-astra` 之外的僵尸项；`gpt-6` 不在记录中，未登记。

**验证**：新增 3 项 SSE 测试（正常流 / 只有 `output_item.done` 的退路 / 空流必须报错），
全量 **268 项 OK (expected failures=5)**。

**未做**：没有让"同一模型 ID 挂多把 Key 自动轮换"。要做到那样需要把模型记录升级为
"一组凭据"或在调用失败时按码切换同模型的其他记录；当前是一个模型一条记录、一条 Key。

**核实 `gpt-6-astra` 是否可调用 → 不可用，且不是"暂时抽风"**：

- 直连该模型：`MODEL_NOT_FOUND`（HTTP 404）；
- 供应商模型目录（`GET https://aaa.bi/models`，需带 `User-Agent`）实际只有 10 个模型，
  **没有任何 `gpt-6`/`astra`/`reserve` 条目**：`gpt-5.6-sol`、`gpt-5.6`、`gpt-5.6-terra`、

1. **上游原话被整段丢弃**。`models.py` 只把 `e.reason`（"Bad Request"）拼进错误，响应体直接扔掉

### 12. 等待语义导致整个 run 静止（`run_64670df8d7e8`，54 分钟）

**现场**（本地运行库，事件 2449–2548，14:50:47 起，14:51:43 之后再无事件）：

| 任务 | 等待条件（真值） | 结果 |
|---|---|---|
| 主调度 root | `task_ids=[C,A,B], topics=[], deadline=null` | 等"C/A/B **结束**"，而它们在会话中不会结束 |
| 出题人 C | `topics=['player-question','guidance']` | 14:51:17 已把指引 `delivery=inbox` 发给 root |
| 玩家 A | `topics=[root_id,'game']` | 等 root 转发指引 |
| 玩家 B | `topics=['指引','猜词','问题','玩家 B']` | 等 root 转发指引 |

C 的指引发进 root 收件箱后，那 54 分钟里**再也没有任何事件发生**，四个任务全部 waiting。
用户的判断是对的：这不是"等待慢"，是**等待条件在拓扑上不可能被满足**。

**根因（三处，其中两处是代码缺陷而非模型选择）**：

1. **`task_ids` 只有"任务结束"这一种触发**。协作场景里子任务在会话进行中根本不会结束，
   而它会不断发消息——所以"监视一个任务"在模型的心智模型里等于"它有动静就叫我"，
   运行时却只认终态。root 的 `topics=[]` 又让它对 C 的消息**结构性失聪**。
2. **`max_deadline` 从未参与唤醒判定**（真 bug）。`wake_waiters` 里 `expired` 只读 `deadline`，
   而 `deadline` 只由 `timeout_seconds` 产生；`max_wait_seconds` 被存进等待记录后**只被续等逻辑
   用来自我限制**。于是文档里"超过 `max_deadline` 就交还给模型"这句话在任何路径上都不成立，
   `deadline=null` 的等待成了**无界睡眠**。四个任务的 `deadline` 全是 null。
3. **没有任何时限的等待完全没有计时器**。`_renew_deadline` 对"无 task_ids/topics"的等待直接返回
   False，兜底也不存在，只能靠外部事件或人工取消结束。

**修法**：

- `wake_waiters` 重写匹配：`task_ids` 同时意味着"**这些任务发来的消息也算事件**"。
  只订阅 `topics` 的等待**保持严格过滤**（没有 topic 的消息依旧不唤醒它），
  所以"进度通知不要 wake"的既有语义不变（`test_progress_messages_do_not_wake` 仍通过）。
- `expired` 同时看 `deadline` 与 `max_deadline`：声明的换手时限成为真正的计时器；
  `_renew_deadline` / `_can_renew` 到硬时限即停止顺延（否则模型每次重新 yield 都会把上界往后推）。
- 新增兜底时限 `DEFAULT_WAIT_CEILING`（默认 600 秒，`UNISON_WAIT_CEILING` 可调）：
  模型什么时限都没声明时也一定会有计时器，到点把模型叫起来自己判断，而不是永久静止。
- 新增 `_stall_warning`：订阅的任务**全部在等消息**（不会走向终态）且自己无 topic、无时限时，
  `tasks_yield` 当场返回 `warning`，把"你在等一个不会结束的东西"说在这个工具的结果里。
  这里**只警告不拒绝**是实测后的决定：真正互相等 `task_ids` 的闭环已经被既有的封闭环检测拦住
  （我用 A→C→D 的探针确认过，`reaches()` 必然接住），所以"不可能被满足"的分支根本不可达——
  写了也会是死代码，于是删掉，只保留能真实触发的诊断。
- `tasks_yield` 与系统提示的说明改口径：`task_ids` 的双重含义、`topics` 是严格过滤器
  （漏掉主题就永远醒不过来）、等待一定有兜底时限。

**验证**（4 项新测试，且每一项都**先临时还原成旧实现确认会失败**）：

- `test_message_from_subscribed_task_wakes_waiter`：C 用默认 `delivery=inbox` 发指引 → root 被唤醒（旧码：永久 waiting）。
- `test_replay_of_stalled_run_topology_now_progresses`：**逐字复现该 run 的四个订阅条件**，
  C 投递指引后 root 由 waiting 转 queued，且不再产生 `RunStalled`（旧码：永久 waiting）。
- `test_wait_without_timeout_still_has_a_timer`：声明 `max_wait_seconds` 的等待必须真的会到点醒来（旧码：无期限）。
- `test_wait_without_any_deadline_gets_ceiling` / `test_wait_on_tasks_that_only_wait_for_messages_warns`：兜底时限存在、静止风险当场警告。
- 全量：**248 项 OK (expected failures=6)**。

**未修（如实记录）**：没有自动"收割"卡死运行的作业。超时兜底已经保证每个等待都会在
`DEFAULT_WAIT_CEILING` 内醒来，因此静止不再是无界的；但一个真的没人推进的 run 仍会保持
`active` 并继续占用工作区目录（新建同目录运行会报"项目目录已被未结束任务占用"），需要人工取消。

### 11. 持续服务型 Agent × 收件箱并发（C/C3 被判负的根因）

**现场**（本地运行库 `.unison/state.sqlite3`，任务 `task_b03179024568` @ seq 2375、
`task_0f8e1b660ca6` @ seq 2112，两次都是 `TaskFailed: 仍有 1 条未处理消息；请继续处理收件箱后再完成`）。
事件序列逐条对齐后，真实时序是：

| seq | 事件 | 含义 |
|---|---|---|
| 2354–2357 | `TaskClaimed` → `InboxBatchReady{remaining:0}` → `ModelCalled` | C 开始这一轮，**收件箱在步骤开始时就被清空** |
| 2366–2367 | `agents_send` → `MessageDelivered` | 玩家 B 的问题在 C **推理期间**到达；`deliver` 发现 C 正在运行，因此只入队、不打断 |
| 2373–2374 | `ModelReturned{content:"是"}` | C 按提示词只回了一个字的纯文本，**没有调用任何工具** |
| 2375 | `TaskFailed` | `complete()` 撞上那条未读消息，抛 `ValueError` → C 判负；换 C2/C3 替补在同一位置以同样方式再死一次 |

**根因是两件事叠在一起**：

1. **模型的纯文本没有消息语义**（架构冲突）。运行时把"无工具调用"一律当成交付
   （`_model_round` 里 `complete(summary=content)`），而持续服务型角色（出题人、主持人、
   答疑者）的正常产出本来就是纯文本——"这一轮答完了"和"这个任务结束了"被混为一谈。
   证据：同一轮里 C 的答复**没有送达任何一方**（`ToolCalled` 为空），判负之后这条"是"成了孤儿。
2. **检查与使用之间存在时间窗**（TOCTOU）。收件箱在步骤开始时清空、在 `complete()` 时复查；
   两者之间隔着几秒的模型推理，并发的第二条消息正好落在这个窗口里，于是必然被判负。
   `deliver` 对正在运行的任务只能入队，没有"打断在飞推理"的机制，所以这个窗口不能被消除，只能不被当成错误。

**修法（`.unison` 层的，不动调度骨架）**：

- 新增 `Runtime.unsettled_reasons(t)`：纯文本轮次能否交付的判据——未读消息 / 自己发出尚未被答的请求 /
  未完成子任务。它与 `complete()` 的守卫**共用同一判据**，区别只在处理方式。
- 新增 `Runtime.defer_text_round(t,reasons,text)`：把这一轮**退回队列**（`TaskQueued` +
  `TextRoundDeferred` 事件 + 一条带 `reasons` 的指引消息：答复用 `agents_send(in_reply_to=…)`、
  等待用 `tasks_yield`、确实做完才用 `tasks_complete`），**不抛错、不判负**。
  模型下一轮能看到自己的纯文本与那条指引，自己决定怎么表态。

### 7. 模型可用性维护：把"验证"降级为真实使用的副产品

**问题**：可用性只有一个写入点（`Models.verify()`），结论**没有时间维度**。于是
(a) 真实调用成功不会回写，目录里长期留着过期结论；(b) 一次瞬时 400 就让模型永久显示"不可用"；
(c) 控制台那个按钮会把 provider 下**每个模型**都真实调一次。实测证据：`gpt-5.6-luna` 用同一个
裸 ping 连续两次得到相反结论（400 → 200），`gpt-5.6-terra` 在"不可用"状态下被主调度选中并
完整跑完 12 轮猜词；两者都是旧结论在误导。

**做法**：三个信号，成本从低到高。

- **主证据 = 真实调用**（成本 0）：`Models.invoke()` 是唯一传输路径，成功即写
  `state=ok, source=call, expires_at=now+24h` 并清零失败计数；失败按码分流。
- **免费旁证 = `/models` 扫描**：某模型重新出现在广告里时，清掉基于"不存在/未广告"的旧结论
  （`discover()` 里做，不需要额外请求）。
- **补充 = 主动探测**：只补"过期或从未验证"的空档；新增维护作业 `model-health`
  （6 小时一次，`MAX_PROBES_PER_RUN=3`，按最久未验证优先，支持预演，静默）。

**失败分流**（决定"重试有没有用"）：`AUTH`/`MISSING_CREDENTIAL`/`NO_ADAPTER`/新增的
`MODEL_NOT_FOUND`(404) → 需要人处理，`blocked` 且 `needs_probe=false`，**不重试**；
`RATE_LIMIT`/`QUOTA`/`SERVER`/`TIMEOUT`/`TRANSPORT` → 瞬时，单次不改变结论、连续 3 次才降级；
`INVALID_REQUEST`/`CONTEXT_WINDOW_EXCEEDED`/`EMPTY_RESPONSE` → 与"这段时间能不能用"无关，只记错误。
一次 **probe 失败不会推翻**未过期的真实调用成功证据，只写 `ModelHealthDisagreement`。

**兼容**：旧 `reachability` 只读投影成 `health`（标 `legacy`、视为已过期），永久错误与**陈旧 6 小时以上**
的参数类错误投影为 `blocked`（避免用探测反复确认一个不存在的模型），其余为待复验；首次 `save()` 平滑升级。
`reachability` 字段继续输出，控制台不必同步升级。

**本轮修掉的四个自身缺陷**（都是实现过程中被测出来的）：
(a) `checked_at`/`expires_at` 分别调用 `now()`，导致 `expires_at != checked_at + TTL`（测试断言抓到）；
(b) 失败路径把 `source` 无条件写成当次来源，导致 probe 失败后"真实调用"的证据来源被抹掉；
(c) 维护路由默认 `{"dry_run":true}` **覆盖了作业策略**，真探测静默变成预演（真机上表现为"点了没反应"）；
(d) 旧记录里的 `INVALID_REQUEST` 一律投影为待复验，会让 `gpt-reserve` 这类 404 模型每 6 小时被
白白探测一次 → 新增 `MODEL_NOT_FOUND` 且按新鲜度分流。

**真机验证**（真实 Key、真实上游）：
- 预演：`6 个待复验，本次会探测 3 个`，按最久未验证排序，**0 次调用**；
- 真探测：3 次调用 → `gpt-5.6` 转 `ok(probe)`、`gpt-reserve` 转 `blocked(MODEL_NOT_FOUND)`、`gpt-5.2` 仍 `unknown`；
- 复验后立刻再预演：只剩 3 个（刚验证过的**一个都没再打**），`blocked` 模型 `needs_probe=false`；
- 真实调用回写：用 `gpt-5.6-luna` 跑了 1 个真实小任务（写 `probe.txt` 并提交），其 health 立刻变成
  `source=call / needs_probe=false / failures=0 / stale=false`——目录不再靠猜。

### -1. 会话历史改为从事件日志派生（`derive_history`）

- 派生实现与 DSH 的 `deriveMessages` 同构：两阶段（收集 → 代入），压缩用**全量代入**——每个 `ContextCompacted` 把"这一刻之前累积的历史"替换为"头部两条 + checkpoint + `kept_from` 之后的原文"。为此在压缩事件里显式记录 `kept_from`，让压缩算法与派生共用同一定义，彻底去掉下标推算。
- 升级期规则：任务一条消息事件都没有（升级前的数据）时保留缓存副本，不被空派生结果覆盖；一旦有消息事件，日志即为事实源。
- 过程中修掉三处实现缺陷：(a) 记录 body 是序列化 JSON 字符串，派生必须解析后再遍历；(b) `apply_compactions` 覆盖了收集阶段算出的 `linked`，导致派生结果被误判为"无日志"；(c) 压缩的 `kept_from` 语义与"保留最后两轮"不一致，导致派生与缓存相差一条。
- 新增 `Runtime.seed_history()`：导入、测试或恢复脚本要成批写入历史时走这条路径（写日志 + 计数），直接改 `task['history']` 会与日志分叉。

**第二步（本轮同时完成）：任务记录不再保存历史副本。** 记录里只留 `history_messages`（消息数）与 `history_ref`（最后一条引用），因此**任务记录大小与对话长度无关**，追加消息不再重写整段历史——之前那份"平方写入"随之消失。`GET /api/task` 的 `history` 由服务端按需派生；`HistoryCacheMismatch` 换成 `HistoryDerivationShortfall`（派生条数与计数不一致时的报警）。升级前创建的任务仍从记录的 `history` 字段读取，不改写。

### 0. 统一维护层 + 知识层与验证证据修复

**统一维护层（`unison/maintenance.py`）**：把原先散落在调度循环里的定时逻辑收成一处。

- 作业只声明 `id / description / interval / initial_delay / dry_run / destructive / loud` 与 `run(store, dry_run)`；注册表负责依赖注入（需要运行时的作业用 `needs_runtime` 声明）、到期判定、状态持久化（`maintenance` 记录）、事件记录与错误隔离。
- 到期判定在连续失败后**指数退避**（上限 6 小时）；**破坏性且不支持预演的作业永不自动执行**，只能显式触发；`dry_run` 只传给声明支持的作业。
- 高频作业（工作区扫描）保持静默不写完成事件，避免污染事件流；失败始终写 `MaintenanceFailed`。
- 注册的内置作业：`workspace-scan`(2s，只读)、`benchmark-refresh`(24h)、`object-gc`(7d，破坏性，默认预演)、`archive-retention`(7d，破坏性，默认预演)、`knowledge-maintenance`(6h，只读、按相对阈值)。
- 插件可 `runtime.maintenance.register(job)` 加入自己的作业；`GET /api/maintenance` 查看状态，`POST /api/maintenance/run` 手动触发。

**对象回收（mark & sweep，默认预演）**：递归标记所有记录与事件引用的内容对象。过程中发现并修掉两个真实缺陷：(a) 记录 body 是**序列化 JSON 字符串**，只做"整串是否哈希"判断会漏掉清单里的全部引用——会把活对象当成垃圾，现在先解析再递归；(b) 字典分支的递归被一个错误的 `if` 嵌套挡住，只扫描到第一个 64 位字符串。两处都补了回归测试。

**扫描 stat 短路**：`Workspace.scan()` 增加 `stats` 指纹（`mtime_ns + size → hash`），未变文件直接复用旧哈希；任务记录新增 `file_stats`。大仓库下 2 秒一次的扫描不再重读整个仓库。

**知识层修复**：

- 任务完成不再自动发布报告到知识库（报告本来就在 `report` 记录里），消除"知识库堆满任务报告"的噪音；只有模型显式调用 `broadcast` 才产生知识。
- 来源按 `scope` 记录：`project` 按项目根比对，`workspace` 按发布它的子工作区比对；同一文件两处都存在且内容一致时按项目记。修掉"父任务在自己工作区找不到子任务来源文件 → 有效知识全被判失效"。
- 发布时写反向边 `dependents`，`Workspace.invalidate()` 改为按依赖图**双向**传播；旧记录没有该字段时退回前向扫描。
- `knowledge_search` 改为**全部词命中**（AND）+ 标题权重 + 相关度排序 + 条数裁剪，并可用 `include_stale=False` 只取有效知识；依赖缺失不再是 `KeyError` 而是明确的失效原因。

**验证证据分级**：报告新增 `verification_evidence`，把模型声明与运行时核对结论分开——`verified_by_command`（证据绑定到执行记录且退出码 0）/ `verified_by_inspection`（只有目视证据）/ `unverified`。声明 `verified` 但无命令证据时带 `unconfirmed: true` 并写 `VerificationUnconfirmed` 事件；程序不强制模型跑命令。

### 1. 请求可重建、压缩可还原、中断可区分（借鉴 DSH 的三条机制）

- **每次模型调用落一条请求信封**（`request` 记录，`GET /api/requests`）：保存 provider/模型/协议/地址、系统提示词原文与其 sha256、工具 schema 与其 sha256、输入快照引用、消息数与输入字节数、以及记录时的全局事件游标 `seq`。`GET /api/request?id=` 可用这些引用**逐字重建** `config`/`prompt`/`messages`/`tools`，不依赖任何进程内状态；相同提示词与 schema 按内容寻址去重，逐条记录成本很低。`ModelCalled` 事件改为引用 `request_id`，报告新增 `request_headers` 列表。
- **压缩改为遮蔽语义**：checkpoint 记录 `shadowed_range`、被遮蔽区间的 `region_ref` 与被压缩前历史的 `history_ref`；`restore_history()` 能把任意一次请求的输入还原到"这次压缩之前"，`depth=None` 可逐层一路还原到最初原文。`ContextCompacted` 事件同样带上 `shadowed_range`、`kept_tail`、`messages_before`。修复了上一版 `restore_history` 用压缩**之后**的快照下标去切原文的缺陷（改为直接读 `region_ref`，不做任何下标推算）。
- **中断的工具调用区分两种语义**：调用表里没有记录 → `TOOL_NOT_STARTED`（工具未开始，确认后可直接重试）；已记录但无结果 → `TOOL_OUTCOME_UNKNOWN`（结果未知，有副作用时不得盲目重放）。每次修复写一条 `ToolRepairRecorded` 事件。

### 1. 主动 compact 改为当轮立即生效

- `context_compact` 不再等到"下一轮开头"才消费。模型调用该工具后，运行时在**本轮工具批次执行完毕**的位置立即压缩，并在**同一次调度**里用压缩后的上下文继续模型调用；不需要人工批准，也不消耗额外一轮调度。
- 为此把 `step()` 拆成"循环 + 单轮"两层：`step()` 负责消费 `compact_requested`／容量超限并在压缩后继续，`_model_round()` 负责一次模型调用加工具批次。单次调度内连续压缩上限 `MAX_COMPACT_PER_STEP=3`，超过即明确报错而不是无限循环。
- 保持原有安全语义：压缩点固定在工具调用成对落盘之后，模型当轮的工具结果留在保留尾部；同一轮里若以 `tasks_complete` / `tasks_yield` / `human_ask` 结束，则不压缩、不改写历史，标志位保留。
- 修复压缩切分边界缺陷：当"最后两轮完整交互"已经覆盖到历史开头时，`cut` 会落到首两条消息之前，压缩结果会把一个**列表**当消息拼进 `history`（表现为任务直接失败：`'list' object has no attribute 'get'`；若命中 no-tool 分支还会触发属性错误）。现在 `cut` 被夹在 `[2, len(history)]`，且可压缩区间为空时只清标志、不调用模型、不改写历史。
- 工具返回文案与控制台提示改为"立即生效"。对正在等待的任务，压缩仍需下一次被调度时才生效。

### 2. 凭据成为模型可用的能力

- 新增 `models_credentials` 工具：按需返回明文 `api_key`、`base_url`、wire api、请求头、上下文与输出上限；每次读取写一条 `CredentialsExposed` 事件用于审计。
- `workspace_shell` 注入 `UNISON_MODEL_ID` / `UNISON_MODEL` / `UNISON_MODEL_BASE_URL` / `UNISON_MODEL_API` / `UNISON_MODEL_API_KEY`，以及 `key_env` 指定的同名变量。模型因此可以在自己写的脚本里直接调用模型接口，而不必只依赖 `tasks_submit` 委派。
- 凭据只存在于子进程环境，不写工作区文件，因此不进入文件清单、差异、报告与归档；`GET /api/models/credentials` 为外部程序提供同一份事实。
- `SYSTEM` 提示同步更新：说明 compact 立即生效、凭据可用于调用、但不要写进文件/报告/知识。

### 3. HTTP API 服务化

- 外部调用令牌：`--api-token` > `UNISON_TOKEN` > 数据目录 `api_token`（首次启动生成，权限 0600，启动时打印）。同源控制台（`Origin` 与 `Host` 一致）免令牌，其它来源必须带 `Authorization: Bearer <token>` 或 `X-Unison-Token`。
- 稳定错误契约：`auth_required`(401) / `invalid_request`(400) / `internal_error`(500)，响应体同时保留 `error` 文案，控制台行为不变。
- 新增 `GET /api/wait?task_id=&timeout=`：阻塞等待任务进入终态或需要人工介入（`waiting` 时返回 `wait` 条件），窗口上限 900 秒，HTTP 侧超时自动放宽。
- 新增 `GET /api/models/credentials`：明文凭据目录。
- 新增 [docs/API.md](docs/API.md)：鉴权、错误码、端点说明与端到端示例。

## 保留边界与后续工作

1. 压缩仅在工具批次边界执行；等待中的任务要等下次被调度才压缩。同源免令牌只承诺本机单用户场景，本机其它进程可伪造 `Origin`。
2. 凭据以明文进入模型上下文与子进程环境；报告不写凭据，但能力上要求"模型可信"。若需要隔离，应改为按任务签发短期令牌或代理调用。
3. 恢复日志用于本地单进程运行时，未承诺断电耐久性、全目录瞬时原子可见性或跨数据目录锁；外部编辑器不受项目占用检查约束。
4. Git 元数据、依赖目录、符号链接和大文件仍不复制；权限仅包含普通 Unix rwx 位，不含 ACL、所有者与扩展属性。
5. 文件扫描、归档与部分配置网络请求仍同步运行；`/api/wait` 使用 100ms 级轮询而非事件订阅。当前状态以 records 恢复，回放不等于完整事件溯源；插件仍是工具/适配器扩展。
6. 报告保存执行事实与模型声明，但不自动识别任意 shell 是否属于测试，也不强制固定验收命令。
7. 真实模型协作、compact 约束保持与单 Agent 对照评测仍待执行；本轮新增的凭据、服务化与维护层同样只做了机制验证。
8. 对象回收只做"无引用即回收"，**没有按保留期筛选**：一个刚产生但确实无人引用的对象会被下一次非预演执行删掉；归档的 tar.gz 里虽有副本，但对象与归档之间没有引用关系记录，所以删对象前应当先确认归档策略。归档清理只列出与显式删除，没有自动保留期。
9. 派生历史每次需要扫描该 run 的全部事件（有按游标的内存缓存）；单个 run 的事件到十万级时应改成按任务增量订阅。旧任务的历史字段会一直留在记录里，直到被显式清理。
10. 工作区扫描仍是全量遍历目录（只是不再重读未变文件的内容），没有文件系统事件订阅；文件数达到十万级时需要重新评估。
10. 知识整理目前只**报告**哪些项目该整理，不会自动提交整理子任务（避免维护层直接调用模型）；真正的合并/刷新入口仍未实现。
11. `verification_evidence` 只区分"有没有绑定到执行记录"，不判断那条命令是否真的是测试命令——这仍依赖模型与人工。
12. 技能层是**目录包 + 目录注入 + 按需加载**，没有实现 DSH 的 provider 注册表、分层作用域与依赖/生命周期管理：技能根目前写死在 `roots_for()` 里，自定义根只能由代码设置，`skills/reload` 之外没有技能变更的主动推送（靠维护作业与目录指纹）。技能正文信任本地文件内容，没有签名或来源校验。
14. 模型可用性维护只覆盖"这套凭据 + 这套参数下能否返回一次响应"：不判断模型是否擅长任务，也不感知账户额度、上游限流窗口或供应商在两次探测之间改变策略。`ok` 的 24 小时 TTL 是经验值，不是 SLA；`blocked` 的自动清除只挂在配置变更与 `/models` 扫描上，若供应商单方面恢复某模型而配置未动，要等 TTL 到期后的复验。
15. 技能端口调用只有 `bridge` 一种实现（独立进程 + stdin/stdout JSON），没有把技能做成进程内服务或插件；桥接脚本继承本机权限，与本机代码同等可信，没有沙箱、配额或按技能的凭据隔离。作业状态只在内存里排队（持久化的是状态记录），进程重启后 `queued`/`running` 的作业不会被续跑，必须重新提交。并发上限 4 与批量上限 8 是写死的常量，未做配置化。
13. 内置 image-generation 技能的可用性随上游策略变化：匿名档开放的模型由供应商决定（当前 `/image/models` 只返回 `sana`），接口也没有承诺 SLA 或内容策略；生成结果只校验"确实是图像"，不判断是否符合需求，也不做内容审核。Hugging Face 分支只有错误路径经过实测，尚无 token 环境下的成功实测。

## 第六轮：按"简洁、优雅、让 AI 自主决定"做的一次清理

触发：用户指出项目里掺杂了不该有的东西——**多余的边界维护、硬标准、限制 AI 发挥的 skills**，
违背了"简洁、优雅"的核心思想。这一轮做的是**减法**，判据是设计文档自己写的两句话：

- §1：「运行时保留少量与任务内容无关的不变量：调用格式合法、任务不被重复领取、结果不覆盖较新的版本、取消有效。**这些是执行语义，不是替 AI 编写业务决策树。**」
- §13：验证方式等由 AI 选择。

诊断下来所有问题共享一个根因：**运行时在用正则、计数器与阈值做 AI 规模的判断**（"这条 shell 的退出码算不算数"、"这轮纯文本算不算交付"、"这个等待还等不等得到"、"这批证据够不够可信"）。
每一条当初都是为了堵一次真实事故，但堵法都是"再加一个守卫"，于是守卫层本身成了负担。
处置统一为：**保留事实与测量，去掉判词与拦截**。

### 6.1 运行时删掉的东西

| 位置 | 删除内容 | 为什么它不该在运行时 |
|---|---|---|
| `exit_code_is_masked()` | 6 条正则把 shell 命令分类成"退出码被吞掉"（heredoc / 管道 / `sed -i` / 多行无 `set -e` / 文件操作） | 正则命中不等于检查没通过；命令原文与退出码已经记录，判断留给读报告的人 |
| `verification()` / `manifest_digest()` / `evidence_drift()` / `changed_after_evidence()` | 证据分级 `verified_by_command` / `_weak` / `_inspection` / `unverified`，退出码掩盖判定，执行清单 vs 交付清单的漂移判定，`VerificationUnconfirmed` 事件 | §13 说验证方式由 AI 选择。运行时现在只把证据绑定到执行记录并原样保留命令、退出码、是否超时 |
| `MAX_TEXT_DEFERRALS = 2` + `defer_text_round` 的抛错分支 | 连续 3 轮纯文本就抛 `RuntimeError` 把任务判负 | 用计数器代替"这活干完没有"；模型没犯错。现在退回次数不设上限，照常说明待办 |
| `complete()` 的未完成子任务硬阻塞 | 有非终态子任务就拒绝交付 | §5 明确交付时机由主模型决定。保留"未读消息不能丢"这一条（那是投递语义） |
| `MAX_WAIT_RENEWALS` / `DEFAULT_WAIT_CEILING` / `ALL_IDLE_GRACE` / `_renew_deadline()` / `_can_renew()` / `_all_idle()` | 等待到期静默顺延、无时限时补 600 秒兜底、全体空闲 45 秒后把人叫起来并投 `all-idle` 说明 | 用运行时的钟表安排模型的作息。§5.2 的语义是"无事件时不调用模型轮询"；时限改由模型自己声明 |
| `MESSAGE_DEDUP_WINDOW = 120.0` + 内容去重分支 + `MessageDeduplicated` | 120 秒内相同内容 + 发送者 + kind 的消息被压制 | "两次相同内容是不是同一件事"是语义判断；催促/重发/确认都可能是两次真实意图。只保留 message_id 去重 |
| `HEAVY_CALL_LIMIT` + 拒绝分支 | heavy 档调用数上限，超了就 `ValueError` | 配额是人的策略，不是运行时该写死的东西。改为只统计并如实报告用量 |
| `_stall_warning()`（并修掉**连续调用两次**的重复） | 遍历任务状态预测"这个等待永远不会被满足" | 改名 `_wait_observation()` 并降级为**描述**：只说订阅对象当前的状态与"除消息外没有事件会唤醒你"，不预测、不拦截 |
| `GROUPS` / `tools_profile`（`lean`/`readonly`） | 按角色预制工具档位，裁掉 context_compact 等 | 与系统提示里"所有模型同等工具能力"直接矛盾；用不用得上某个工具是模型的判断。现在所有 Agent 拿同一套 28 个工具 |

### 6.6 这一轮的取舍与遗留

- **等待现在真的可能长眠**：删掉兜底时限后，一个"无事件、无时限"的等待只能靠其他任务的消息或人类唤醒。
  这正是 §5.2 的语义，但与当初修"整个 run 静止 54 分钟"的意图相反。缓解在于：等待登记时会
  `observation` 说明边界，`tasks_yield`/系统提示都明确要求声明时限或订阅真实事件。
- **"证据够不够"现在完全靠人读**：报告不再替人区分"跑了测试"和"测试真的过了"。
  命令原文、退出码、是否超时、以及"文件在最后一条命令之后又改过"都在报告里，
  但没有任何自动结论。这是有意的——判据脆弱时，自动结论比没有结论更危险。
- 工具 schema 固定为全量 28 个（约 13.9 KB / 次调用）：删掉档位后每次调用的固定开销回来了，
  这是"所有模型同等能力"的代价。
