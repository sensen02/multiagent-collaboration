# 知识条目：A 卡出废图的头号原因（coopmat）

**结论先说**：本机（AMD RX 9070 XT / RDNA4 / gfx1201 / RADV）用 stable-diffusion.cpp 生图时，
**必须** `export GGML_VK_DISABLE_COOPMAT=1`。不设它，出图是"大面积同一块灰 + 窄竖条噪声"，
而且**退出码 0、文件也在、尺寸也对**。代价约 +13%（512×512/6 步：2.60s → 2.95s）。

## 症状长什么样

| 指标 | 不设（废图） | 设了（正常） |
|---|---|---|
| 最常见颜色占比 | **0.63–0.81** | 0.001–0.33 |
| 那个颜色是什么 | `128,121,11x`（零潜变量解码出来的灰） | 正常画面色 |
| 抽样色数 | 6 400 左右（但都挤在一起） | 13 000–32 000 |
| 8×8 块均值标准差 | 0.017–0.035（没有结构） | 0.09–0.28 |
| PNG 体积（512×512） | 40–160 KB | 550–700 KB |

看 ASCII 缩略图更直观：不是图像，是**纯噪声 + 每 16 列一个重复列**。

## 为什么之前没人发现（教训在检查器身上）

第一版 `imagecheck.py` 只看"列均值竖纹"和"16 级颜色桶数"——
按列平均恰好把"几乎所有像素都一样"这件事**平均掉**了，于是把废图判成"未发现退化特征"，
还进了交付报告。**检查器本身也需要标定**：现在按**像素本身**取值
（主色占比 > 0.40 即废图），并用已知好图/废图回归验证过。

标定时还踩到两个假阳性，都已修：

- **像素素材天然"大片纯色背景"**（主色占比可以到 0.62），所以"主色占比高"必须与
  "有没有结构（块 std、色数）"合起来看，不能单判；
- **受限调色板的像素图只有 4–16 色**，"色数少"本身不是缺陷，只有"色数少 **且** 没有结构"才算废图。

## 复现与验证（各 3 行）

```bash
B=/srv/unison-assets/bin/sd-cli
M=/srv/unison-assets/models/sd15/GuoFeng3.4.safetensors
P="guofeng style, a sword on silk, misty courtyard"

$B -m $M --backend vulkan0 -p "$P" -W 512 -H 512 --steps 6 --seed 74000 -o bad.png   # 40 KB 级别、主色 0.79

GGML_VK_DISABLE_COOPMAT=1 $B -m $M --backend vulkan0 -p "$P" -W 512 -H 512 --steps 6 \
  --seed 74000 -o good.png                                                            # 620 KB、主色 0.001

python3 <gpu skill>/scripts/imagecheck.py bad.png good.png
```

## 已落进技能的地方

- `gpu/SKILL.md`：最小可用命令默认带这个变量；把"不必设 coopmat"那句**错的旧结论**改掉了。
- `gpu/references/failure-modes.md`：新增"第零问：coopmat 关了吗"作为排查第一顺位。
- `image-generation/scripts/local_image.py`：本机后端**默认**在子进程环境里设这个变量，
  并把 `coopmat_disabled` 写进每张图的溯源——修好了还要**可追溯**，否则下一个人以为这是默认行为。
- `gpu/scripts/imagecheck.py`：判定改成按像素取值，并做了好图/废图/像素素材三类回归。

## 可复用的判据

1. **"退出码 0 + 文件存在 + 尺寸正确"不是图像有效的证据**——这三条废图全满足。
2. 修好的东西要写进**执行体**（默认值），不要只写进文档：文档会被下一次重构冲掉。
3. 检查器也要有**回归样本**：这次是"检查器把废图判成正常"，比废图本身更危险。
4. 判断阈值要按**实测分布**标定（好图 0.001–0.33 vs 废图 0.63–0.81），不要凭感觉取 0.5。
