# 多模型协作融合方案：初步设计

日期：2026-09-11。范围：本地七个仓库的 README、部分调度入口及官方资料核对；不是完整源码审计，也未运行框架或完成性能对比。下面的缺点是机制带来的工程取舍，不代表各框架没有对应补救功能。

## 1. 判断

可以吸收这些系统的机制，设计一个按任务难度调度模型、以可验证产物推进的协作系统。不能预先保证优于单模型；必须在相同预算下验证。

多智能体与多模型是两个维度：多个角色可以使用同一模型，一个角色也可以更换模型。角色提示词不同并不保证能力互补。新系统应将角色、模型、工具、工作流分别配置。

## 3. 吸收什么，以及付出什么

| 来源 | 值得吸收 | 机制的代价与新方案处理 |
|---|---|---|
| MetaGPT | SOP、明确分工、分阶段产物 | 全套流程增加小任务开销；只给复杂任务启用完整流程 |
| AutoGen | 消息驱动、可选择发言者、工具与模型扩展 | 对话和选人本身消耗预算；采用定向消息、轮次与成本上限 |
| ChatDev | 分阶段交接、配置式工作流与可视化方向 | 固定链限制适应性，可配置图又增加配置负担；提供模板并允许受限返工 |
| CrewAI | 角色和任务配置、Flows 与团队组合 | 嵌套委派使实际执行路径难预测；限制委派深度并记录每次调度 |
| LangGraph | 显式状态、分支循环、检查点 | 状态和节点仍需业务设计；统一产物与状态契约 |
| CAMEL | 专家交互、Workforce 分解及恢复 | 共享上下文和协调增加成本；按需检索，局部讨论 |
| AgentVerse | 专家分配、求解反馈循环 | 评估模型也可能出错；将外部证据和程序验证纳入验收 |
| DyLAN | 依据贡献选择团队、动态通信 | 预选成本与评分偏差；先用可解释规则，再用历史评测校准 |
| Generative Agents | 记忆检索、反思与规划 | 反思可能固化错误；仅将验证过的经验升级为长期知识 |

LangGraph 的持久执行和状态能力见[官方概览](https://docs.langchain.com/oss/python/langgraph/overview)。这类能力可作为底座，不能代替业务正确性验证。

## 4. 建议架构

目标先聚焦“代码修改与验证”，因为有文件差异、测试和构建等相对明确的验收依据；这是建议的首个场景，并非假定用户只需要编程。

执行链：需求与验收条件 → 任务图 → 模型路由 → 执行 → 验证 → 交付。验证失败时只返工受影响节点及其下游；调度器不能自行放宽验收条件。

### 统一内核

- Task：目标、输入产物版本、依赖、验收条件、预算、截止时间、状态。
- Agent：职责、工具权限、模型选择策略、输出结构。角色与模型解耦。
- Artifact：文件或结论、来源、内容哈希、生成者、验证状态。
- Event：调度原因、调用、结果、成本、重试、检查点，支持追踪与恢复。
- Verdict：通过/失败/证据不足，附测试结果、失败案例或来源；“大家都同意”不能作为通过依据。

流程和状态转移由程序控制；模型负责提出计划、生成产物及分析问题。计划必须通过依赖合法性、预算和工具权限检查才能执行。

### 按需协作

1. 简单且可验证：单执行者 → 程序验证 → 交付。
2. 中等任务：规划 → 执行 → 独立审查 → 验证。
3. 可分解复杂任务：按依赖并行执行 → 集成 → 独立审查和验收。
4. 关键分歧：最多启用少量独立候选，先独立作答，再比较证据；仍无结论则标注证据不足。

审查者默认不读取执行者的自我评价，但能访问任务、产物和必要来源。使用不同模型是减少同源错误的手段之一，不保证独立性。

### 模型路由

先用可配置能力表：代码、推理、长上下文、视觉、工具支持、结构化输出，以及实测延迟、成本、通过率。按任务要求过滤，再选择预算内候选。不要固定宣称某品牌永远适合某角色。

第一版采用规则和失败升级；累积数据后才考虑学习式路由。指标应包括最终验收贡献、引入缺陷、成本和耗时，不能只看发言次数或模型自报信心。模型版本变更后重新校准。

### 共享产物与执行可靠性

共享区存任务状态、产物引用、证据和未解决问题；模型按需读取相关片段，避免广播完整聊天记录。上下文摘要必须保留来源和未决事项。

代码任务使用隔离工作目录或 worktree，声明文件责任范围，由集成步骤处理冲突；集成之后重跑相关验证。检查点不等于外部操作自动恰好执行一次：工具调用要记录操作标识、结果和幂等策略，对状态不明的副作用先核实。

预算在并行派发前预留，完成后结算；同时限制调用数、token、时间、并发和返工次数。额度不足时明确结束为未完成并保存产物。禁止以截断结果伪装成功。

## 5. 第一版边界

建议复用 LangGraph 作为可替换的运行底座，自建任务契约、模型适配层、路由与验收层。吸收其他项目的设计机制，不同时嵌套七套运行时。

第一版包含：命令行入口、可配置模型适配器、规划/执行/审查职责、三种流程模板、共享产物目录、持久化事件与检查点、预算限制、失败升级、测试命令验收。先提供确定性的离线适配器验证编排，再接真实模型测量能力。

后续再做可视化流程编辑、长期经验库和学习式调度。具体供应商和模型由可用账号及目标任务评测确定。

示例：用户要求修改登录逻辑。规划者形成改动范围和验收标准；执行者提交补丁；审查者检查兼容性及边界；测试工具给出结果。失败反馈只交给相关执行节点，修复后重新集成验证。小改动可以跳过单独规划调用。

## 6. 如何证明融合有效

采用相同任务集、相同工具和上下文、相同预算上限，比较：单强模型、同模型多角色、固定多模型团队、自适应融合方案。规划、预选、审查、失败重试与集成开销全部计入。

先收集一组有独立验收标准的真实任务，按难度和类型分层，重复运行并报告波动。记录成功率、每个成功任务成本、端到端耗时、人工干预次数和恢复成功率。测试不应完全由生成实现的同一个模型决定。

做消融：移除动态路由、独立审查、共享产物或记忆，观察哪一项确实改善结果。若复杂流程在简单任务上只增加成本，调度策略应退回单模型。只有实测结果改善质量—成本—延迟取舍，才能声称融合产生收益。
